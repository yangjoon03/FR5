# FR5 로봇 Python SDK - 한국어 카테고리별 예제 모음

이 저장소는 [FAIR-INNOVATION/fairino-python-sdk](https://github.com/FAIR-INNOVATION/fairino-python-sdk)
(FR5 로봇의 공식 Python SDK) 저장소의 **Linux SDK**를 가져와서, 다음
작업을 한 것입니다.

1. SDK 안의 `example/` 폴더에 있던 **150개 넘는 정리되지 않은 예제
   스크립트**(날짜 이름 스크래치 파일 다수 포함, 전부 중국어 주석)를
   **기능 카테고리별로 재구성**
2. 모든 함수 설명·파라미터 설명을 **중국어 → 한국어로 번역**
3. 예제 코드와 실제 SDK(`code/fairino/Robot.py`) 소스를 대조해서,
   버전이 바뀌며 어긋난 부분(**SDK/예제 불일치**)을 찾아 수정하고 문서화
4. 이동(Move) 계열 함수는 "파라미터가 뭘 의미하는지"뿐 아니라
   **"실제로 로봇이 어떻게 움직이는지"**까지 자세히 설명

원본 SDK가 왜 중국어인지: FR5는 중국 FAIRINO(非诺)사의 협동로봇이고,
SDK 문서(`@brief`, `@param` 주석)가 전부 중국어로만 작성되어 있습니다.
이 문서는 그 내용을 이해하고 재정리한 결과물입니다.

> ⚠️ 이 문서와 예제 코드는 **로봇이 실제로 연결되지 않은 상태**에서
> SDK 소스코드를 읽고 정리한 것입니다. 실기 동작 테스트는 하지 않았으니
> 처음 실행할 때는 반드시 저속(`vel` 낮게)으로, 충돌 반경을 확보한
> 상태에서 확인하세요.

## 이 저장소(fork)를 왜 이렇게 재구성했나 (windows/ 폴더가 사라진 이유)

원래 공식 저장소는 최상위에 `linux/`와 `windows/` 두 폴더가 나란히
있는 구조입니다(리눅스용 SDK와 윈도우용 SDK를 한 저장소에 같이 배포).
이 fork(`yangjoon03/FR5`)는 **리눅스 환경만 사용**하므로 다음을 정리했습니다.

- `windows/` 전체 삭제 - 안 쓰는 플랫폼의 SDK/예제/바이너리
- `linux/libfairino/`(C 확장 소스) 삭제 - 파이썬 예제 학습에는 불필요
- `linux/fairino/build/`, `__pycache__/`, `*.so`/`*.pyd`/`*.pyc`/`*.o`
  등 컴파일 산출물 삭제 - 소스가 아니라 빌드 결과물이라 저장소에
  남길 이유가 없음(각자 환경에서 다시 빌드/설치하면 됨)
- `linux/example/`(정리되지 않은 원본 예제 150여 개) 삭제 - 이 내용은
  사라진 게 아니라 **`code/examples/` 아래 카테고리별로 재구성되어
  들어있습니다**
- 최종적으로 `linux/` 접두사 자체를 없애고, 저장소 최상위가 바로
  `code/`가 되도록 평탄화

즉, 이전에 이 fork의 Test 브랜치를 처음 만들었을 때는 "리눅스+윈도우
전체 SDK 원본"이 그대로 올라가 있었는데, 이번 정리로 "리눅스용, 카테고리별
정리 버전"만 남도록 바꿨습니다.

## 공통 사용 순서

```python
from fairino import Robot

robot = Robot.RPC("192.168.58.2")   # 1. 연결
robot.ResetAllError()               # 2. (필요시) 에러 초기화
robot.RobotEnable(1)                # 3. 활성화 - 이거 없으면 Move 계열 전부 실패
robot.MoveJ(...)                    # 4. 이동
```

# 2. 이동(Movement) - 각 방식이 실제로 어떻게 움직이는가

`code/examples/02_movement/`에 있는 모든 이동 함수는 "파라미터"보다
**"경로의 모양(geometry)"**을 이해하는 게 훨씬 중요합니다. 아래는
방식별로 실제 로봇 팔이 어떤 궤적을 그리는지 정리한 것입니다.

## 2.1 MoveJ - 관절 공간 이동 (`01_move_joint.py`)

**동작 원리**: 6개 관절 각각이 "지금 각도 -> 목표 각도"까지 독립적으로
보간(interpolation)되며, **모든 관절이 동시에 출발해서 동시에 도착**하도록
속도 프로파일이 맞춰집니다. 즉 관절 공간에서는 각 관절이 자기 나름의
직선(각도 대 시간 그래프가 직선에 가까움)을 그리지만, 그 결과로 로봇
손끝(TCP)이 3차원 공간에서 그리는 경로는 **일반적으로 곡선**이고
미리 예측하기 어렵습니다.

```
관절 공간에서는 부드러운 궤적          그런데 TCP(손끝) 궤적은 휘어짐
  j1 ─────╲                                     ___
  j2 ──────╲___                             ___/   \
  j3 ───────╲__                            /         \___
             (동시 도착)                  시작           도착
```

**언제 쓰나**: 경로 모양이 중요하지 않고 "그냥 A자세에서 B자세로
가장 빠르고 부드럽게 이동"하고 싶을 때 (예: 웨이포인트 사이 이동,
안전위치 복귀). 장애물이 없는 열린 공간에서 가장 빠르고, 특이점
(2.6 참고) 문제도 잘 생기지 않습니다.

**주의**: `desc_pos`는 필수가 아니라 참고용 기본값입니다 - 비워두면
`joint_pos`로부터 정기구학을 계산해서 채웁니다. `blendT`가 `-1.0`이면
그 지점에서 완전히 멈췄다가(블로킹) 다음 동작을 실행하고, `0~500ms`
값을 주면 그 지점 근처에서 멈추지 않고 다음 동작과 이어붙습니다(논블로킹).

## 2.2 MoveL / MoveL1 / MoveL2 - 데카르트 직선 이동 (`02_move_linear.py`)

**동작 원리**: TCP가 시작점에서 목표점까지 **반드시 3차원 공간의
직선**을 따라 이동합니다. 자세(회전) 역시 시작 자세에서 목표 자세까지
구면 보간(SLERP과 유사)되어 점진적으로 바뀝니다. 이 직선을 만족시키기
위해 매 순간 로봇 컨트롤러가 역기구학을 계산해서 각 관절이 어떻게
움직여야 할지 역산합니다.

```
TCP는 항상 이 직선 위를 지나감
  시작 ●───────────────────────● 목표
       (관절들은 이 직선을 만들기 위해
        각자 복잡하게 움직임 - 사람 눈엔 안 보임)
```

**언제 쓰나**: 용접선, 디스펜싱 경로, 삽입 동작처럼 **경로 자체가
정확히 직선이어야 하는 작업**. 대신 MoveJ보다 계산량이 많고, 직선
경로 중간에 관절이 갈 수 없는 자세(관절 한계, 특이점)를 만나면
그 자리에서 에러가 날 수 있습니다.

`MoveL1`/`MoveL2`는 같은 MoveL을 살짝 다른 매개변수 구성으로 감싼
버전입니다(`MoveL2`는 `status` 파라미터가 추가됨) - 신규 코드에서는
기본 `MoveL`을 쓰고, 구버전 SDK와의 호환이 필요할 때만 1/2 버전을
참고하세요.

## 2.3 MoveCart - 데카르트 점대점 이동 (`02_move_linear.py`)

**동작 원리**: 목표 좌표는 데카르트 좌표(mm/°)로 주지만, 실제 이동
경로는 MoveJ처럼 **관절 공간 보간**을 사용합니다. 즉 "목표는
좌표로 지정하되, 가는 길은 직선을 보장하지 않는" 절충형입니다.

**언제 쓰나**: 목표 자세는 좌표로 편하게 지정하고 싶은데, 경로가
직선일 필요는 없고 오히려 **특이점 근처를 자연스럽게 피해가길
원할 때**. MoveL보다 특이점에 안전합니다.

## 2.4 MoveC - 원호(Arc) 이동 (`03_move_arc_circle.py`)

**동작 원리**: **세 점**(현재 위치, 경유점 P, 목표점 T)을 지나는
하나의 원호를 계산해서 그 호를 따라 이동합니다. 세 점이 하나의
원을 유일하게 결정하므로(3점은 항상 하나의 원 위에 있음), 경유점을
어디에 찍느냐가 곧 "호의 굽은 정도"를 결정합니다.

```
        경유점 P
          ●
        ╱   ╲
      ╱       ╲
현재●            ● 목표점 T
   (세 점을 지나는 원의 일부 = 원호)
```

**언제 쓰나**: 모서리를 둥글게 돌아가야 하는 경로, 배관/파이프
형상을 따라가는 용접/디스펜싱.

## 2.5 Circle - 완전한 원 이동 (`03_move_arc_circle.py`)

**동작 원리**: MoveC와 같은 3점(현재+P+T) 기준으로 원을 계산하지만,
호의 일부만 도는 게 아니라 **그 원을 한 바퀴(360°) 전부 돌아 시작
위치로 복귀**합니다.

```
        ● P
      ╱───╲
    │       │   ← 한 바�퀴를 다 돌고 시작점으로 복귀
      ╲───╱
        ● T
```

**주의**: 한 바퀴를 전부 돌기 때문에 MoveC보다 훨씬 넓은 반경의
공간이 필요합니다 - 실행 전 주변 장애물과의 충돌 반경을 원의 지름
기준으로 확인하세요.

## 2.6 NewSpiral - 나선(스파이럴) 이동 (`03_move_arc_circle.py`)

**동작 원리**: 원운동을 하면서 **매 바퀴(회전)마다 반지름을 조금씩
늘리거나 줄이고**, 동시에 회전축 방향으로도 조금씩 이동할 수 있습니다.
즉 "평평한 원 여러 개"가 아니라 3차원 스프링/코일 같은 궤적을 그립니다.

```
위에서 본 모습(반지름 증가)      옆에서 본 모습(축 방향 진행)
     ╭───╮                         ╱╲  ╱╲  ╱╲
   ╭─┤ ╭╮ ├─╮                     ╱  ╲╱  ╲╱  ╲
  │  ╰─┴┴─╯  │   (바퀴마다 커짐)  ─────────────→ 진행방향
   ╰─────────╯
```

**언제 쓰나**: 원형 디스펜싱/씰링 패턴, 원형 용접 패턴 채우기.
`param`(7개 값)으로 회전수/기울기/초기반지름/반지름증가량/축증가량/
회전방향/속도모드를 지정합니다. ⚠️ **발견한 이슈**: 구버전 예제는
`param`을 6개짜리로 호출하는데, 현재 SDK는 7번째 값(`velAccMode`)까지
읽으므로 7개를 다 채워야 `IndexError`가 나지 않습니다.

## 2.7 ServoJ / ServoCart - 실시간 서보 스트리밍 (`04_move_servo_realtime.py`)

**동작 원리**: 지금까지의 Move 함수들은 "목표 지점 하나를 주면 로봇이
알아서 가속-정속-감속하며 이동"하는 **한 번의 명령**이었습니다. ServoJ/
ServoCart는 반대로, **아주 짧은 주기(기본 8ms)마다 계속 "다음 위치"를
새로 보내주는** 방식입니다. 로봇은 그 위치들을 최대한 따라가려고
매 순간 반응합니다 - 마치 사람이 손으로 계속 조금씩 미는 것을
로봇이 실시간으로 쫓아가는 것과 비슷합니다.

```
일반 Move: [출발] ────(로봇이 알아서 가속·정속·감속)──── [도착]  (명령 1번)

ServoJ:    [pos1][pos2][pos3][pos4]...  (8ms마다 다음 목표를 계속 보냄)
            ↓     ↓     ↓     ↓
           로봇이 매 순간 "지금 받은 목표"를 향해 짧게짧게 이동
```

**언제 쓰나**: 외부 센서(비전, 힘센서)로 매 순간 목표를 보정해야 하는
실시간 추종 제어, 컨베이어 트래킹, 힘 제어와 결합한 표면 추종.
일반 Move보다 훨씬 정교한 제어가 가능하지만, 스트리밍이 끊기지 않게
호출자가 직접 루프를 관리해야 하는 부담이 있습니다.

## 2.8 SplinePTP / NewSplinePoint - 스플라인(다중점 부드럽게 잇기) (`05_move_spline.py`)

**동작 원리**: 여러 개의 목표점을 미리 등록해두면, 로봇은 그 점들을
**각 점에서 멈추지 않고** 하나의 부드러운 곡선으로 이어서 지나갑니다.
일반 MoveL을 여러 번 연달아 호출하면 점마다 감속→정지→재가속이
일어나 울퉁불퉁하게 움직이지만, 스플라인은 그 점들 사이를 매끄러운
곡선(스무딩)으로 연결합니다.

```
MoveL을 여러 번:      ●──정지──●──정지──●──정지──●   (덜컹거림)

스플라인(NewSpline):  ●～～～～●～～～～●～～～～●   (한 번에 부드럽게)
```

**언제 쓰나**: 로고 그리기, 곡면을 따라가는 폴리싱/디스펜싱처럼
여러 점을 매끄럽게 이어야 하는 작업. `NewSplineStart(type)`의
`type=0`은 각 점 주변에서 원호로 부드럽게 넘어가고, `type=1`은
지정한 점을 그대로 통과합니다.

## 2.9 StartJOG / StopJOG - 조그(수동 점동) (`06_move_jog.py`)

**동작 원리**: 목표 좌표를 주는 게 아니라 "어느 축을, 어느 방향으로"만
지정하면, `StopJOG`(또는 `ImmStopJOG`)를 호출할 때까지 **그 방향으로
계속** 움직입니다. 티치펜던트의 방향 버튼을 누르고 있는 것과 완전히
같은 동작입니다.

**언제 쓰나**: 수동 위치 조정, 티칭 준비 단계. 자동화 프로그램
안에서는 거의 쓰이지 않고, 사람이 개입하는 상황에 사용합니다.

## 2.10 AngularSpeedStart - 자세 회전 속도 지정 (`08_angular_speed_and_accel_scale.py`)

**동작 원리**: MoveL의 `vel`은 기본적으로 위치(직선) 속도 기준입니다.
그런데 위치는 거의 안 바뀌고 자세(회전)만 크게 바뀌는 이동(제자리에서
손목만 90° 돌리는 등)에서는, 위치 속도 기준만으로 계산하면 자세가
너무 빠르게 홱 돌아갈 수 있습니다. 이 함수를 켜두면 그 구간 동안은
"자세 회전 속도"를 별도 비율(0~300%)로 관리해 더 부드럽게 만듭니다.

## 2.11 PointsOffsetEnable - 포인트 오프셋 (`07_move_points_offset.py`)

**동작 원리**: 좌표 자체는 그대로 두고, 그 뒤에 실행되는 Move 명령의
목표 좌표에 **일괄적으로 오프셋(위치 이동값)을 더해서** 실행합니다.
같은 궤적 프로그램을 팔레트 위 여러 칸에 반복 적용할 때, 매번 좌표를
다시 계산하지 않고 오프셋만 바꿔서 재사용할 수 있습니다.

# 4. 발견한 SDK ↔ 예제 불일치 모음

원본 `example/`의 스크립트들은 SDK 버전이 여러 번 바뀌는 동안 갱신되지
않아, 현재 `code/fairino/Robot.py`의 실제 함수 시그니처와 어긋나는
부분이 있었습니다. 이 저장소의 예제 코드에는 아래 내용이 모두
수정 반영되어 있습니다.

| 함수 | 문제 | 현재 SDK 기준 수정 |
|---|---|---|
| `NewSpiral` | 예제가 `param`을 6개 값으로 호출 | `param`은 7번째 값(`velAccMode`)까지 필요. 6개만 넘기면 `IndexError` |
| `ServoCart` | 예제가 `exaxis` 인자를 생략 | `exaxis`는 기본값이 없는 필수 인자. 생략하면 `TypeError` |
| `FT_Control` | 예제가 `sensor_num`/`force_torque`/`gain` 키워드 사용 | 현재는 `sensor_id`/`ft`/`ft_pid`로 이름이 바뀜. 옛 이름 사용 시 `TypeError` |
| `SetDexterousHandsMove` | 일부 예제 문맥상 인자 개수가 헷갈림 | 실제로는 `(idstart, slaveNum, pos, speed, force, max_time)` 6개 인자 필요 |
| `SoftwareUpgrade` | 예제 주석에 두 번째 인자가 불명확 | 실제 의미는 `block`(True=완료까지 대기, False=즉시 반환)이며 "재부팅 여부"가 아님 |
| `SetVelReducePara` | 예제 주석이 각 값의 의미를 물음표로 추측 | 실제로는 `enable`(0=끔/1=수동모드/2=전체모드), `maxTCPVel`, `strategy`(0=정지경고/1=자동감속/2=정지후비활성화) |
